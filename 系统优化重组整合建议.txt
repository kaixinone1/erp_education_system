2.3 salary_info 与 salary_data 合并说明
  两表存储的都是"工资变动历史记录"（非"最新工资数据"）。

  合并的作用：
    1. 消除数据重复：两表存储同类数据，salary_info更完整（多370条正常升级记录）
    2. 统一数据源：后续所有工资相关功能只需查询一个表
    3. 降低维护成本：不需要维护两个表，不需要担心数据不一致
    4. 与"经常更新"不冲突：每次更新是"新增一条变动记录"，不是修改现有记录

  合并方式：
    - 将 salary_data 中 salary_info 没有的记录补入 salary_info
    - 统一字段名（id_card_1 → id_card, field_21 → salary_level）
    - 删除 salary_data 表

  获取最新工资方法：
    SELECT * FROM salary_info WHERE id_card='xxx' ORDER BY time DESC LIMIT 1;

七、绩效工资管理
================================================================================

7.1 定位
  - 绩效工资是工资的组成部分，归属工资管理
  - 但由分管人事的管理员独立管理，需要一个相对独立的入口
  - 放在工资管理下作为子模块

7.2 与通用模板系统的关系
  通用模板系统中的"义务教育学校教职工绩效工资审批表"是绩效管理的主表。
  绩效工资审批功能应直接跳转到该模板的填报页面。

7.3 业务流程
  1. 绩效工资审批 → 基于通用模板"义务教育学校教职工绩效工资审批表"生成
  2. 审批表扫描上传 → 上级审批后的PDF扫描件上传保存
  3. 绩效工资历史 → 按年月查询历史审批表
  4. 绩效工资统计 → 汇总、计算、核算
  5. 绩效标准设置 → 管理岗位等级对应的绩效工资标准

7.4 数据迁移
  当前绩效管理数据存储在JSON文件中，需迁移到PostgreSQL数据库。
  相关数据库表：performance_pay_approval、performance_pay_remarks、performance_pay_standards

十一、职称信息与岗位聘任整合
================================================================================

11.1 两表当前数据
  ┌──────────────────────┬──────────────────────┐

  │ （职称信息）          │ （岗位聘任）          │

  │ 496人                │ 412人                │
  │ 两表关联匹配：411人   │                      │
  │ 仅职称表：85人        │ 仅聘任表：1人         │
  └──────────────────────┴──────────────────────┘

11.2 业务关系
  教师通过职评获得任职资格（职称）→ 通过岗位聘任实现职务与岗位挂钩
  → 聘用后才能享受对应工资待遇

  职称取得时间 ≤ 聘任时间（先评职称，后聘任）

11.3 整合方案：不物理合并，建立主从关联 + 统一维护界面

  主表：teacher_title_info（职称信息）
    - professional_title_1：职称名称（一级教师、高级教师...）
    - field_70：批准文号
    - time：职称取得时间
    - unit_2：评审单位
    - unit_3：批准单位

  从表：post_appointment_info（岗位聘任）
    - job_title：岗位名称（六级专技、八级专技...）
    - post_time：聘任时间
    - xue_duan：学段（小学/初中）
    - shi_fou_yi_ping_wei_pin：是否已评未聘
    - shi_fou_zhan_gang：是否占岗

十二、历史快照与时光倒流
================================================================================

12.1 设计原则
  - 不新建日快照（经讨论不需要）
  - 仅保留月快照和年快照
  - 采用独立历史记录表（非JSONB），便于查询
  - 软删除（is_deleted标记），不物理删除

12.2 所有业务表统一新增字段
  ALTER TABLE 表名 ADD COLUMN is_deleted  BOOLEAN DEFAULT FALSE;
  ALTER TABLE 表名 ADD COLUMN deleted_at  TIMESTAMP;
  ALTER TABLE 表名 ADD COLUMN created_at  TIMESTAMP DEFAULT NOW();
  ALTER TABLE 表名 ADD COLUMN updated_at  TIMESTAMP DEFAULT NOW();

12.3 历史快照表设计
  CREATE TABLE data_history_snapshots (
      id               SERIAL PRIMARY KEY,
      table_name       VARCHAR(200) NOT NULL,       -- 快照的表名
      snapshot_type    VARCHAR(20) NOT NULL,        -- monthly / yearly
      snapshot_period  VARCHAR(7) NOT NULL,         -- 2025-08（月）或 2025（年）
      snapshot_data    JSONB NOT NULL,              -- 完整数据快照
      record_count     INTEGER DEFAULT 0,           -- 快照记录数
      created_at       TIMESTAMP DEFAULT NOW()
  );

  CREATE INDEX idx_snapshot_lookup 
    ON data_history_snapshots(table_name, snapshot_type, snapshot_period);

12.4 快照策略
  - 月度快照：每月1日凌晨自动执行，保留2年
  - 年度快照：每年1月1日凌晨自动执行，保留10年
  - 手动快照：用户手动触发

12.5 时光倒流查询
  -- 查询2025年8月的教师基础信息快照
  SELECT snapshot_data FROM data_history_snapshots
  WHERE table_name = 'teacher_basic_info'
    AND snapshot_type = 'monthly'
    AND snapshot_period = '2025-08';

  -- 查询2025年全年的教师基础信息快照
  SELECT snapshot_data FROM data_history_snapshots
  WHERE table_name = 'teacher_basic_info'
    AND snapshot_type = 'yearly'
    AND snapshot_period = '2025';

12.6 前端界面
  在教师管理页面增加"历史数据"按钮：
    - 按月查看：选择 2025年8月 → 展示该月数据快照（只读）
    - 按年查看：选择 2025年 → 展示该年数据快照（只读）

13.3 统一标准
  - 错误处理：统一 try-catch + 用户友好的中文错误提示
  - 日志：统一使用 Python logging 模块
  - API调用：统一使用 axios 封装，集中在 api/ 目录
  - 数据存储：所有业务数据存入 PostgreSQL，禁止使用JSON文件

13.4 字段名、表名、映射名的统一管理
  核心原则：所有模块调用时通过以下配置获取映射，不硬编码。

  表名唯一来源：table_name_mappings.json（英文→中文）
  字段名唯一来源：table_field_relations 表（英文→中文 + 关联关系）
  字典值唯一来源：dict_* 表（字典编码→中文值）

  调用流程：
    前端请求 → API → 查 table_field_relations 获取映射
    → 查 table_name_mappings 获取中文表名
    → 查 dict_* 获取字典值
    → 返回给前端（所有字段名已经是中文，字典值已翻译）
